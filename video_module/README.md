# Sirena Video

Відео з дрона оператору з мінімальною затримкою: камера на РПі → H.264 →
SRT → MediaMTX на адмін-сервері → WebRTC (WHEP) → браузер.

```
РПі (srt-relay-capture.service, srt_relay_capture.py — один GStreamer-пайплайн)
  v4l2src ─ queue(leaky) ─ [jpegdec] ─ videoconvert(I420) ─ overlaycomposition(мітка часу)
    ─ x264enc(zerolatency, VBV) ─ h264parse ─ mpegtsmux(alignment=0)
    ─ appsink → ts_packer (кадр = 1 буфер) → appsrc ─ srtsink ──SRT/WireGuard──┐
                                                                               │
Адмін-сервер (mediamtx-admin.service, патчений MediaMTX)                      │
  SRT-прийом (gosrt) → MPEG-TS демукс (go-astits) → WebRTC/RTP ◄──────────────┘
                                                        │ WHEP
Браузер (admin_module/templates/_video_player.html) ◄───┘
```
| Файл | Що робить |
|---|---|
| `srt_relay_capture.py` | будує й запускає пайплайн, підключає мітку часу, склейку TS і автобітрейт |
| `capture_relay/config.py` | усі налаштування (env + `sirena_video_config.json` з панелі) |
| `capture_relay/ts_packer.py` | склеює TS-вихід одного кадру в один буфер для srtsink |
| `capture_relay/timestamp_overlay.py` | штрих-код часу в кожному кадрі (наскрізна затримка + офлайн-аналіз) |
| `capture_relay/adaptive_bitrate.py` | контролер бітрейту (без GStreamer, тести — `tests/`) |
| `video_relay.py` | стежить за камерою, пише SRT-ціль у `/etc/default/sirena-relay`, перезапускає захоплення |
| `../admin_module/deploy/mediamtx-patches/` | патчі й готовий бінарник MediaMTX (див. README там) |
| `../additional_modules/lowercam/` | нижня (CSI) камера: перегляд і локальний запис |

## Встановлення

**РПі** — `sudo bash install_rpi.sh http://<admin>:8080` (викликає
`video_module/install.sh`). Інсталятор:
- ставить GStreamer (`plugins-base/good/bad/ugly`, `libav`) і
  `gir1.2-gst-plugins-base-1.0` (GstVideo — потрібен для мітки часу);
- копіює модуль у `/opt/sirena-video`, створює venv;
- **перевіряє**, що є всі елементи пайплайна (`v4l2src jpegdec videoconvert
  overlaycomposition x264enc h264parse mpegtsmux appsink appsrc srtsink`)
  і GstVideo — інакше падає з переліком, чого бракує;
- `install_rpi.sh` пише в `/opt/sirena/.env` дефолти відео (VBV, автобітрейт;
  `KEYINT` навмисно не задається — GOP = fps).

На РПі MediaMTX немає — всі патчі MediaMTX стосуються лише сервера.

**Адмін-сервер** — `bash /opt/sirena-admin/admin_module/deploy/deploy.sh`
→ `install_mediamtx.sh` ставить **патчений** бінарник
`mediamtx-patches/mediamtx-v1.11.3-sirena_linux_amd64` з репо (офіційний
реліз лише як фолбек з попередженням — він повертає +~90мс затримки).
Перезбирання — `mediamtx-patches/build.sh`.

**Годинник:** РПі має бути синхронізована через NTP (systemd-timesyncd за
замовчуванням) — від цього залежать мітка часу в кадрі й вікна Starlink в
автобітрейті.

## Затримка

### Як міряється

`timestamp_overlay.py` малює в кожному кадрі штрих-код з unix-часом (рядок 0 —
момент малювання; рядки 1-2 — повний час захоплення, лічильник, CRC).
Плеєр читає рядок 0 з декодованого кадру → «Наскрізна затримка» в плеєрі й
колонка `e2e_latency_ms` діагностичного CSV
(`/opt/sirena-video/video_latency_logs/<device>/<date>.csv` на сервері).

Це затримка **від малювання мітки до показу**, без внутрішньої затримки
самої камери (тепловізор — 1-2 кадри, USB-грабер ~50мс): її видно лише
зовнішнім тестом (годинник/LED перед камерою, обидва екрани знято телефоном
на 240fps).

Для розкладу по етапах використовувався одночасний запис трафіку на РПі
(wg0) і на сервері (SRT-вхід і WebRTC-вихід MediaMTX): SRT-пакети
зіставляються за номером, годинники вирівнюються за SRT-даними й ACK у
зворотному напрямку (NTP-офсет РПі брехав на ~13мс), кадри — за PTS, час
малювання — зі штрих-коду, декодованого з цього ж трафіку.

### Що було і що виправлено (виміряно 30.09.2026, живий стенд)

| Причина | Де | Втрата | Виправлення |
|---|---|---|---|
| `mpegtsmux alignment=7` відправляє лише повні групи по 7 TS-пакетів; хвіст кадру чекав наступного кадру | РПі | **+33мс** на кожному кадрі | `alignment=0` + `ts_packer.py` (весь кадр одним буфером; srtsink сам ріже по 1316 байт) |
| MPEG-TS демуксер (go-astits) віддавав кадр лише з приходом наступного | MediaMTX | **+33мс** на кожному кадрі | патч: кадр віддається, щойно отримано `PES_packet_length` байт |
| SRT-приймач (gosrt) віддає пакети на 10-мс тіку і лише після ACK | MediaMTX | +0…20мс, вихід прив'язаний до 10-мс сітки | патч: тік 1мс, віддача без очікування ACK |
| Прийомна затримка SRT захардкоджена 120мс | MediaMTX | +120мс (виправлено раніше) | патч: 10мс |
| Chrome не вмикає low-latency рендер без RTP-розширення playout-delay | браузер/MediaMTX | ~15мс буфера | патч: playout-delay min=max=0 → буфер 0мс |
| Дві повні конвертації кадру (YUY2→BGRx→I420) під cairooverlay | РПі | ~2-3мс + CPU | одна конвертація, мітка через overlaycomposition у I420 (-24% CPU) |
| Великі I-кадри (дефолт x264 VBV 600мс; I у 5-10 разів більший за P) і `KEYINT=15` | РПі/мережа | сплески, черги, втрати на вузькому лінку | `vbv-buf-capacity=100`, GOP = fps |

Результат на тому самому стенді:

| | До | Після |
|---|---|---|
| малювання → вихід WebRTC з сервера (p50 / p90) | 74.7 / 79.9мс | **32.3 / 34.1мс** |
| буфер Chrome (jitterBufferDelay) | 15мс | **0мс** |
| наскрізна в браузері, p50 | 111мс | **69мс** (C270 720p MJPEG), **48-60мс** (тепловізор 640x512) |

Залишок ~32мс до виходу з сервера: кодування ~7мс, мережа ~2мс, SRT-буфер
20мс (`SRT_LATENCY_MS` на РПі, див. компроміси), обробка ~3мс. Далі —
мережа до оператора, декодування (~2мс) і показ (vsync монітора: у
середньому ½ кадру, 8мс на 60Гц; монітор 144Гц дає -5мс).

## Автобітрейт

`capture_relay/adaptive_bitrate.py`, працює лише з програмним x264enc (на
RPi5 апаратного енкодера немає). Ціль — бітрейт з панелі; контролер тримає
нижче, коли лінк не витягує.

Сигнали зі статистики srtsink кожні 250мс:
- **черга**: RTT вище мінімального за 10с — вузьке місце (Starlink, шейпер)
  накопичує чергу ще до втрат;
- **втрати**: пакети, про втрату яких повідомив приймач (NAK). Увага:
  libsrt рахує кожен NAK-звіт, а gosrt повторює звіт кожні 20мс — частка
  завищена в рази, тому в оцінці ємності вона обмежена.

Рішення:
- **перевантаження** (черга > 30мс і росте; або втрати > 10% з чергою; або
  стійкі >0.75с втрати без черги — шейпер без буфера) → одразу ~85% від
  оціненої ємності лінку (за ростом черги `C = rate/(1+dq/dt)` і/або за
  втратами; береться менша), далі пауза, поки ефект не дійде (≥ RTT) —
  перервана, якщо черга не спадає;
- **стояча черга** > 30мс довше 1с (бітрейт ≈ ємності) → зріз, щоб злити
  її за ~секунду;
- **випадкові втрати 2-10% без черги** (радіоканал) → не різати, рости
  повільно; **одиночний сплеск** втрат (ключовий кадр на лінку з пачковими
  втратами) ігнорується;
- **ріст**: адитивно біля оціненої ємності (спершу 3с постояти), ×1.08/с
  звичайно, ×1.25/с на старті, після 10с без перевантажень, далеко нижче
  оцінки або коли вже вище старої оцінки (лінк розширився); поки черга
  ≥15мс — не рости;
- **Starlink**: супутник перемикається кожні 15с у фіксовані секунди
  хвилини (12/27/42/57) — ~70мс розриву й стрибок RTT, що не є нестачею
  ємності; у вікні 11.8-13.5с кожного циклу рішень не приймається.
  `ADAPTIVE_BITRATE_STARLINK_GUARD=auto` вмикає це лише при базовому RTT
  ≥15мс;
- старт з 50% цілі, нижня межа абсолютна (150kbps), ціль змінюється з
  панелі (з перезапуском сервісу).

Кожен зріз і раз на 10с стан пишуться в журнал (`journalctl -u
srt-relay-capture | grep AdaptiveBitrate`); раз на секунду стан іде на
адмін-сервер (`/api/video/report-bitrate`) і потрапляє в діагностичний CSV
(`/opt/sirena-video/video_latency_logs/<device>/<date>.csv`, рядок на
секунду, поки відкритий плеєр): `rpi_current_kbps` / `rpi_target_kbps` /
`rpi_min_kbps` — бітрейт, `rpi_rtt_ms` — RTT з libsrt, `rpi_queue_ms` —
черга (RTT мінус мінімальний), `rpi_loss_pct` — втрати за NAK-звітами
(завищені, див. вище), `rpi_abr_state` — стан контролера (`start`,
`increase`, `probe`, `settle`, `hold`, `lossy`, `overuse`, `drain`,
`guard`). Поруч — браузер (`e2e_latency_ms`, `jitter_buffer_ms`, ...) і
MediaMTX (`srt_*`). Якщо набір колонок змінився посеред дня, попередній
файл дня відкладається як `<date>_vN.csv`.

### Результати

Тести на моделі лінку (`python -m pytest tests/`): чистий лінк — без
зрізів; шейпер 1.5М з маленьким буфером — 96% ємності; сходинки
5/1/3/0.6/5М з буфером 300мс — 92%, черга p90 8мс; Starlink-модель — 94%.

Живий тест на стенді 30.09 (шейпінг лише відеопотоку на wg0 РПі:
10 → 1 → 3 → 0.6 → 10 Мбіт/с, буфер 300мс):

| | Старий контролер | Новий |
|---|---|---|
| реакція на падіння ємності | 2-7с | 0.45-0.63с |
| бітрейт нижче нової ємності | — | ~1с |
| повернення після розширення лінку | ~40с | 6-16с |
| використання каналу 1.5М | 52% | ~95% |
| наскрізна затримка під обмеженням (p50) | 200-875мс | 55-60мс |

Після різкого обвалу ємності перші 2-3с затримка сягає ~1с — черга, що
встигла накопичитись у мережі до першої реакції.

Шейпінг для власних тестів (на РПі, лише UDP на порт 8890 — SSH і
телеметрію не зачіпає; обов'язково прибрати після):
```bash
sudo tc qdisc add dev wg0 root handle 1: htb default 20
sudo tc class add dev wg0 parent 1: classid 1:20 htb rate 500mbit
sudo tc class add dev wg0 parent 1: classid 1:10 htb rate 1000kbit ceil 1000kbit burst 15k
sudo tc qdisc add dev wg0 parent 1:10 handle 10: bfifo limit 37500   # ~300мс
sudo tc filter add dev wg0 protocol ip parent 1: prio 1 u32 match ip protocol 17 0xff match ip dport 8890 0xffff flowid 1:10
sudo tc class change dev wg0 parent 1: classid 1:10 htb rate 600kbit ceil 600kbit burst 15k   # змінити швидкість
sudo tc qdisc del dev wg0 root                                                                 # прибрати
```

## Налаштування (`/opt/sirena/.env`)

| Змінна | Дефолт | Що |
|---|---|---|
| `VIDEO_DEVICE` | `/dev/video0` | камера (краще `/dev/v4l/by-id/...-video-index0`) |
| `SRT_LATENCY_MS` | 20 | SRT-буфер (ефективно = max з сервером, там 10). Міняти через рестарт `video-relay.service` |
| `KEYINT` | = fps | кадрів між ключовими; не задавати без причини |
| `X264_SPEED_PRESET` | ultrafast | пресет x264 |
| `X264_VBV_BUF_MS` | 100 | буфер ratecontrol x264, мс |
| `H264_PROFILE` | main | baseline / main / high |
| `VIDEOCONVERT_THREADS` | 2 | потоки конвертації в I420 |
| `ADAPTIVE_BITRATE` | 1 | автобітрейт (панель має пріоритет) |
| `ADAPTIVE_BITRATE_INTERVAL_MS` | 250 | період рішень |
| `ADAPTIVE_BITRATE_MIN_KBPS` | 150 | нижня межа |
| `ADAPTIVE_BITRATE_STARLINK_GUARD` | auto | вікна Starlink: auto / 1 / 0 |

Ширина/висота/fps/бітрейт/ввімкнення автобітрейту — з панелі
(`sirena_video_config.json`, пріоритет над env). На сервері:
`SIRENA_WEBRTC_PLAYOUT_DELAY_MAX_MS` у середовищі `mediamtx-admin` (0 —
показувати кадр одразу; ≤500 — з легким згладжуванням; від'ємне — вимкнено).

## Компроміси й відкриті питання

- **SRT-буфер vs Starlink.** 10-20мс достатньо для стабільного лінку (RTT
  стенду ~2мс). На Starlink (RTT 40-60мс, розриви ~70мс на перемиканнях)
  повторна передача в це вікно не встигає — втрачений пакет = артефакт до
  наступного ключового кадру. Стійкіший варіант — 80-120мс (+60-100мс
  затримки). Рішення — після польотів зі Starlink.
- **playout-delay 0** вимикає згладжування показу в Chrome: на нерівній
  мережі кадри показуються так само нерівно, як приходять.
- **Камера.** Внутрішня затримка камери в заміри не входить. USB-веб-камери
  з MJPEG (C270) додають ~38мс на декодування/конвертацію 720p до мітки —
  для тепловізора (YUYV) цього немає.
- **Нагрів.** РПі на стенді — 77-80°C, з'являвся soft temp limit; при 80°C+
  Pi 5 знижує частоту, що б'є по кодуванню. Потрібне охолодження.
- **Нижня камера** (`additional_modules/lowercam`): перегляд через
  `rpicam-vid | ffmpeg` без `--low-latency` (на Pi 5 без нього програмний
  кодер тримає до ~8 кадрів) — ще не оптимізувалось.
- Колонка `rpi_bandwidth_mbps` — оцінка ємності від libsrt; контролер її
  не використовує (шум 3…2000 Мбіт/с), лишена для порівняння.
