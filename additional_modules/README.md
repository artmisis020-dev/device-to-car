# Sirena Additional Modules

Контейнер для бортових (РПі), latency-критичних "легких" функцій — на
противагу `vision_module` (Spark, важкі GPU-моделі: класифікація/детекція
об'єктів). Спільна риса модулів тут: обробка кадру дешева (CPU), а
затримка мережі до окремої машини (Spark) неприйнятна.

## Модулі

- **`pixel_tracking/`** — тонкий Flask control-API (порт 9075) для
  піксель-трекінгу цілі по кліку. Сам трекінг (template matching) фізично
  виконується всередині `video_module/srt_relay_capture.py` через
  GStreamer `tee` (`capture_relay/track_tap.py`) — не в цьому процесі й не
  через окрему віртуальну камеру. Цей control-API лише вмикає/вимикає
  прапорець у `/opt/sirena/.env` і передає ціль/забирає статус через
  файли. Причина такої архітектури (і чому попередня, v4l2loopback-based
  ітерація не прижилась) — детально в `pixel_tracking/README.md`.

## Спільна архітектурна ідея

Кожен модуль тут — окремий сервіс з власним control-API (стиль
`sirena_manager/app.py`: тонкий Flask-шар над об'єктом-станом), розгортається
незалежно (`install.sh`, власний venv у `/opt/sirena-<модуль>`).
`pixel_tracking` — виняток у тому сенсі, що САМА обробка кадрів живе не тут,
а всередині критичного відео-пайплайна (за явним, вимкненим за замовчуванням
прапорцем) — але цей control-API як зовнішній інтерфейс і далі не є
залежністю відео-пайплайна: якщо цей процес впаде, трекінг просто лишається
в поточному стані (увімкнено/вимкнено), відео не зачіпається.

Керування (старт/стоп/клік) — завжди з адмін-панелі (ПК), як і для решти
функціоналу цього проєкту; модулі тут лише виконують команди, не
ініціюють нічого самі.
