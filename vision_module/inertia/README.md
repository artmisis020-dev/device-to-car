# Інерційна навігація дрона (IMU dead-reckoning + EKF)

Офлайн-розрахунок траєкторії з MAVLink/dataflash логів, звірка з GPS, детекція jam/spoof.

## Код

**Ядро:**
- `imu_math.py` — спільна математика (матриця повороту, конвертація одиниць)
- `airframe.py` — визначення типу апарата (мультиротор/літак) з MAVLink
  `HEARTBEAT.type` і дефолти ZUPT/NHC/airspeed за типом (див. розділ
  "Мультиротор vs літак" нижче)
- `estimator.py` — простий пороговий dead-reckoning (ZUPT + баро-фільтр)
- `ekf_estimator.py` — **основний Kalman filter** (6-стан: позиція+швидкість). Корекції: `update_baro`, `update_position`, `update_velocity`, `update_zupt` (з дебаунсом), `update_nhc`, `update_airspeed`
- `ekf_wind_estimator.py` — експериментальний варіант з вітром як частиною стану (8-стан) — **дав гірший результат за просту версію**, лишений як задокументована невдала спроба
- `inertial_nav.py` — **бортова інерційна навігація** (`navigation_module`): працює БЕЗ Starlink. Два фільтри: `pure` (чиста інерція: ATTITUDE/RAW_IMU + власний барометр) і `aided` (та сама інерція + ОПЦІЙНІ абсолютні фікси — зараз Starlink, далі візуальна навігація/GPS; χ²-гейт, перезахоп, запізнілі фікси). Час з годинника FC, сирий лог для офлайн-оцінки
- `nav_log_replay.py` — відтворення бортового сирого логу через `InertialNavigator` (те саме, що порахував би борт з іншою конфігурацією)
- `plot_inertia.py` — графіки: чиста інерція і інерція+Starlink, стара (до 30.09) vs нова версія → `plots/inertia_<політ>.png`. Бортові логи: `--nav-log nav_inertia_X.csv` (кілька — повторити), лог ділиться на польоти за ARM; `--extra-model full` — додатково інша модель руху
- `integrity.py` — монітор цілісності фіксів (серія відкидань k-з-n, сума NIS, CUSUM, порівняння з "вільним" прогнозом)
- `smoother.py` — RTS-згладжування (офлайн)
- `air_data.py` — калібрування піто/курсу/вітру на фіксах (лише літак; вмикається явно)
- `imu_noise.py` — Allan variance (реальні шуми IMU)
- `starlink_eval.py` — **стенд звірки зі Starlink** (провали, RTS, затримка, спуфінг) — див. розділ нижче
- тести: `test_ekf_estimator.py`, `test_inertial_nav.py` (`python3 test_*.py`)

**Дані / офлайн-прогін:**
- `replay.py` — CSV → `estimator.py`, будує GPS-еталон (LOCAL_POSITION_NED або lat/lon fallback з `GPS_RAW_INT`), стичка EKF origin-reset
- `ekf_replay.py` — CSV → `ekf_estimator.py` з періодичними псевдо-фіксами (симуляція visual/GPS-корекцій). Перевикористовуваний: `run()` + CLI

**Конвертери логів → CSV:**
- `tlog_to_csv.py` — MAVLink `.tlog`/`.rlog`
- `dataflash_to_csv.py` — ArduPilot `.bin` (з airspeed, EKF3-позицією). **`sync_to_imu=True` за замовчуванням** — критично: пише рядок на кожному семплі IMU (~150Гц), інакше похибка зростає на порядок
- `main.py` — живий MAVLink-логер (серійний зв'язок, на самому РПі)
- `mavlink_udp_logger.py` — живий MAVLink-логер на Spark, той самий формат
  CSV/диспетчеризацію (`HEADERS`/`apply_mavlink_message` з `main.py`), але
  джерело — UDP-реле (див. нижче), не серійний порт

## Живе надходження MAVLink на Spark

RPi5 і Spark — обидва "спиці" одного WireGuard-хаба (адмін-сервер) і **не
бачать одне одного напряму** (перевірено: `ping` зі Spark на RPi — 100%
втрат). Та сама причина, чому відео йде не РПі→Spark напряму, а РПі
публікує на MediaMTX адмін-сервера, а Spark читає звідти ж. Для MAVLink —
точно та сама схема, лише реле замість медіа-сервера:

```
RPi mavlink-router          адмін-сервер (хаб)              Spark
[UdpEndpoint spark_relay]   socat -u UDP-RECV:14570   udpin:0.0.0.0:14570
Address=10.0.0.1 Port=14570 → UDP-SENDTO:10.0.0.7:14570 →  mavlink_udp_logger.py
```

- **На РПі** (`mavlink_module/services/mav-router.conf`): додати ще один
  `[UdpEndpoint]`, що шле на адмін-сервер (`10.0.0.1:14570`) — той самий
  `mavlink-router` вже розсилає повний непофільтрований потік на 5 інших
  ендпоінтів, шостий нічого не ламає. Рестарт `mavlink-router.service`.
- **На адмін-сервері**: `socat -u UDP-RECV:14570 UDP-SENDTO:10.0.0.7:14570`
  — суто байтовий релей, без розбору MAVLink; `-u` — односторонньо
  (RECV→SENDTO), зворотний канал не потрібен (це пасивний тап, не команди).
- **На Spark**: `mavlink_udp_logger.py --listen udpin:0.0.0.0:14570` —
  пише CSV у тому самому форматі, що вже їдять `ekf_replay.py`/`replay.py`/
  `gps_integrity.py`.

Мета зараз — офлайн-перевірка алгоритму на живих даних замість заздалегідь
записаних логів. У майбутньому цей самий UDP-потік піде напряму в
`ekf_estimator.py` онлайн (`predict()`/`update_*()` на льоту замість запису
в CSV), разом з візуальною навігацією — коли обидва дозріють, весь цей
функціонал переїде з Spark у `navigation_module` на самому РПі.

**Аналіз/візуалізація:**
- `gps_integrity.py` — детектор GPS jam/spoof (розриви лінії, деградація фіксу, розбіжність позиції з Doppler-швидкістю)
- `vizualization.py` — покадрова анімація траєкторії (`--start`/`--duration`)
- `route_summary.py` — статичний підсумок усього маршруту одним зображенням
- `ml_experiment.py` — LSTM-заготовка, не доопрацьовувалась

## Бортовий сирий лог (`/home/sirena/logs/nav_inertia_*.csv`)

Пише `navigation_module` через `InertialNavigator` — усе з одним
годинником (wall + час FC), для офлайн-аналізу нових польотів
(`starlink_eval.py --nav-log`). Колонки: `wall, fc_t, type, a..l`; зміст
за типом — `inertial_nav.RAW_LOG_TYPES`: ATT, IMU (RAW_IMU з
магнітометром), IMU2/IMU3, PRS, RALT, GPI (позиція FC — лише еталон), SRV
(виходи моторів), ESC (оберти/струм/напруга), VIB (вібрація), GGA/RMC
(Beitian — незалежний GNSS-еталон), DISH (орієнтація тарілки Starlink),
FIX (Starlink). Частоти запитуються в FC (`navigation_module/config.py`,
`NAV_*_RATE_HZ`); сумарно ≈6.4КБ/с — ~55% UART 115200.

## Звірка зі Starlink (2026-09-30)

Starlink тут — лише ЕТАЛОН для перевірки (і опційне джерело корекцій);
інерція працює без нього. Дані — польоти sirena-P-4 26.09.2026
(`navigation_module/gps_smoothing_eval/data`: RAW_IMU 2Гц, ATTITUDE ~10Гц
з admin-логу), еталон — сирі точки Starlink (повтори відкинуті).
Відтворити: `python3 plot_inertia.py` (графіки), `python3 starlink_eval.py`
(таблиці); новий бортовий лог — `--nav-log nav_inertia_*.csv`.

**Чиста інерція від старту, без жодної корекції** (відстань до Starlink):

| | flight_a медіана / кінець | flight_b медіана / кінець |
|---|---|---|
| стара (HEAD: повний акселерометр) | 1855м / 7.0км | 11.5км / 26.1км |
| нова (нахил тяги + опір 0.5/с) | 269м / 439м | 180м / 325м |

Нова не тікає на кілометри (опір повітря обмежує швидкість), але й РЕАЛЬНИЙ
рух не відтворює — "стояти вдома" дає ~180/156м медіани, тобто на цих
даних чиста інерція не краща за нерухомість. Причина — дані: 2Гц
акселерометр, кути з мережевими мітками часу; прискорення з кутів пояснює
реальну зміну швидкості лише на 20-50% з поворотом 10-30°.

**Інерція + Starlink** — похибка виходу за ~1с до чергової точки
(медіана): стара (MA15 + скид EKF) 27/40м, нова 2.7/3.7м.

**Докочування на провалі Starlink** (медіана похибки, м; flight_a / flight_b):

| провал | стояти на місці | стара | нова (інерція + Starlink) |
|---|---|---|---|
| 2с | 6 / 13 | 30 / 46 | 5 / 7 |
| 5с | 18 / 30 | 34 / 50 | 16 / 19 |
| 10с | 35 / 59 | 59 / 75 | 34 / 43 |
| 20с | 82 / 111 | 130 / 168 | 91 / 91 |
| 30с | 122 / 167 | 235 / 312 | 134 / 134 |

Довідково: модель "стала швидкість" (не інерція) з тими самими фіксами —
3.8/11/25/70/119м (обидва польоти) — поки що краща за інерційну модель.

**Стенд, 2026-09-30 (перший лог з борту на 50Гц, `nav_log_replay.py`):**
модель "hover" читала нахил стенда (−0.6°/−1.3°) як нахил тяги —
хибні 0.25м/с², дрейф ~0.5м/с (242м за 8хв), хоча акселерометр показував
~0 горизонтального прискорення (на землі нахил врівноважує опора).
Виправлено: поки FC не заармлений (HEARTBEAT), швидкість тримається 0 —
на борту чиста інерція на стенді стоїть на 0м. Для довідки: повна модель
("full") на тому ж стенді заармленою дала б 8м за 8хв — у польоті на 50Гц
її ще треба перевірити (на старих 2Гц-даних вона була гіршою).

Виправлені баги: подвійний облік на серії викидів (`anchor += ekf.position`,
EKF при цьому не скидався — до 2.5км за 30с), знак бокової швидкості
оптичного потоку. ZUPT на цих даних шкодить (спрацьовує при висінні в
повітрі) — вимкнено. Частоти підняті (RAW_IMU 50, ATTITUDE 25,
SCALED_PRESSURE 10Гц); наступний крок — перевірити на нових логах.

Літак (`flight_log_2026-09-07_1151_bin_hifreq.csv` — старий лог іншого
борту з ARSP/піто, не sirena-P-4): стала швидкість 11-13% проти 15-27%
з повним акселерометром; після ~1200с GPS у лозі, схоже, спуфлений.
Калібрування піто/курсу/вітру (`air_data.py`) на ньому дало фізично
дивні значення — не використовується.

**RTS (офлайн) усередині провалів 10/20с:** 9-13 → 4-5м / 25-26 → 7-8м.

**Запізнілий фікс** (застосувати в минулому з історії, `history_s`):
затримка 1с — медіана 4.2→3.5м і 7.0→4.6м; 2с — 7.2→5.9м і 12.2→7.1м.

**Цілісність** (`integrity.py`): похибка Starlink не гаусова (медіана NIS
~0.2, середнє ~40 — малий шум + 3-8% стрибків), тому поодинокі відкидання
не тривога. Стрибок 100м: k-з-n ловить 18/19 випадків за 2-3с. Стрибок
30м і повільне "перетягування" 1м/с — здебільшого НЕ відрізнити від
маневру: без справжньої інерційки (стала швидкість) вільний прогноз надто
невизначений. Хибні тривоги k-з-n на чистих даних — 7-56/год залежно від
якості Starlink. На борту — лише попередження в лог.

**Allan variance** (`imu_noise.py`, літак на землі, 50Гц): білий шум
акселерометра 0.002-0.008 м/с²/√Гц — на три порядки менше за оптимальний
q≈3: похибку прогнозу визначає модель руху/кути, не шум сенсора.

## Мультиротор vs літак

ZUPT/NHC/airspeed спираються на протилежні припущення про форму апарата:
ZUPT коректний для мультиротора (реально зависає нерухомо), але хибно
спрацьовує на літаку в рівному польоті; NHC/airspeed писані під
координований політ літака з фіксованим крилом і не мають фізичного сенсу
для мультиротора. `ekf_replay.py` тепер **сам визначає тип апарата** з
колонки `mav_type` (MAVLink `HEARTBEAT.type`, пишеться `main.py`/
`mavlink_udp_logger.py`/`tlog_to_csv.py` — спільний `apply_mavlink_message`)
і застосовує дефолти з `airframe.default_flags()`:

| Тип (`HEARTBEAT.type`) | ZUPT | NHC | airspeed |
|---|---|---|---|
| мультиротор (2,3,4,13,14,15) | on | off | off |
| літак з фіксованим крилом (1) | off | off | off |
| невідомо (нема mav_type у лозі, чи GCS/інший) | off | off | off |

Явний `--zupt/--nhc/--airspeed {on,off}` з CLI (чи `True`/`False` аргументом
`run()`) завжди перекриває авто-визначення; `auto` (дефолт) — саме описана
таблиця. Перевірено наживо (2026-09-23): `sirena-P-4` — `HEARTBEAT.type=2`
(QUADROTOR, ArduCopter), підтверджено і `SERVO_OUTPUT_RAW` (рівно 4 активних
мотор-виходи) — тобто це мультиротор, а НЕ той літак, на польоті якого
знято результати нижче (14.8% медіани й т.д. — інший борт, інші дані).

## Стан і результати (2026-09-23)

**Мета:** інерційка як доповнення visual-навігації — звужувати зону пошуку між
послідовними visual/GPS-фіксами. Цільова похибка: **3% від пройденого шляху**.

**Найкращий досягнутий результат** (реальний маневровий політ літака,
`ekf_replay.py`, без `--airspeed`, інтервал корекції 5с): **14.8% медіани**.
3% не досягнуто.

### Що з'ясувалось

1. **Undersampling у dataflash-конвертері** — головний реальний баг: старий
   10Гц-знімок губив ~93% реальних семплів IMU (~150Гц). Виправлення дало
   покращення на порядок (520% → ~9% на 48-хв лозі).
2. **ZUPT/NHC шкідливі для літака в польоті** — хибно розпізнають рівний
   неприскорений політ як "нерухомість". Корисні лише для стаціонарних/
   повільних апаратів (прапорець `--zupt`).
3. **Airspeed (Піто) без оцінки вітру шкодить** (систематичне зміщення).
   З оцінкою вітру (разовою чи як стан фільтра `ekf_wind_estimator.py`) —
   теж гірше за просту версію на наших даних.
4. **Опубліковані результати** (~5% на 600м, ~2.8% на 1800м, airspeed-aided
   EKF для малих літаків) досягались при вітрі ~3м/с — набагато спокійніші
   умови, ніж, ймовірно, у наших логах (судячи з розбіжності airspeed vs
   GPS-швидкості).
5. **Bias-калібрування акселерометра** (зі стаціонарного періоду перед
   стартом) не дало суттєвого покращення на реальному польоті.
6. **EKF з bias-станом (9-стан)** — bias, зв'язаний через матрицю повороту
   з усіма осями, "просочував" похибку 1D-вимірювань (баро) у горизонтальні
   осі через коваріаційні крос-кореляції. Прибраний зі стану — 6-стан
   надійніший.

### Джерела GPS-еталону

- `LOCAL_POSITION_NED` (пріоритетне, коли є)
- Фолбек: сирий `GPS_RAW_INT.lat/lon` (плоска проекція) — потрібен, коли
  борт не публікує `LOCAL_POSITION_NED`/`GLOBAL_POSITION_INT.lat-lon`
- EKF origin-reset у GPS-даних виявляється й компенсується за порогом
  **абсолютної дистанції** стрибка (>1км), не швидкості — швидкісний поріг
  хибно спрацьовував на звичайному GPS-джиттері

- Розібратись з вітром на реальних даних (потрібні незалежні дані вітру
  для валідації підходу)
- AOA/SSA (кут атаки/ковзання) не логувались на цьому борті — з ними
  airspeed-модель була б точнішою (зараз наближення "вектор вперед по X")
- Спробувати частіші фікси (1-2с) саме на активних маневрах
- `ml_experiment.py` — навчена корекція систематичної похибки, якщо вона
  повторюється від польоту до польоту (потребує кількох логів одного борта)

### GPS-незалежна навігація з камер (дослідження, не реалізовано)

**Керівний принцип (2026-09-24): жоден з нижчеперелічених підходів НЕ є
єдиним/основним джерелом.** Все — IMU/баро (уже є), nadir-потік (уже є),
forward-камера як другий вимір швидкості, MSCKF, monocular depth,
nadir- і forward-visual-navigation — рахується на Spark і фюзиться РАЗОМ
у той самий EKF, кожне джерело зі своєю вагою/довірою (той самий патерн,
що вже є для flow: `quality`→`std`, поріг `min_quality`). Компонент, що
виявиться ненадійним (найімовірніше — forward-camera map-matching, за
результатами дослідження вище), просто отримує менше довіри/відключається
без потреби перебудовувати решту — фільтр спроєктовано саме так, щоб
витримати відсутність чи ненадійність будь-якого окремого джерела.

**Рішення власника (2026-09-24): реалізовувати ОБИДВА класи** —
одометрію (варіанти 1-3 нижче) І візуальну навігацію (абсолютні
map-matching фікси) — разом, у парі з уже готовими інерцією (EKF) та
оптичним потоком, не замість них. Одометрія лишається джерелом
неперервної корекції швидкості між фіксами; візуальна навігація постачає
періодичні абсолютні фікси в той самий `reset_interval_s`/
`update_position()` механізм, що зараз приймає GPS. Коли доходить до
реалізації — почати з варіанту 1 (передня камера), паралельно окремо
проєктувати джерело map-matching фіксів для візуальної навігації.

Уточнення власника: **візуальна навігація працюватиме і з нижньої, і з
передньої камери**, не лише nadir. Важливо для дизайну map-matching:
nadir (вниз) найприродніше зіставляти з супутниковим знімком (той самий
ракурс зверху) — це вже і є той "2026 arXiv, altitude-adaptive
geo-localization" підхід з optical_flow/README.md. Передня камера — інший
ракурс (перспектива вздовж землі, горизонт/об'єкти на дистанції), під
супутниковий знімок напряму НЕ лягає — знадобиться або окрема
референс-база (наземні фото/3D-модель місцевості, landmark-based
localization), або перепроєкція/ректифікація перспективи під приблизно
nadir-вид перед зіставленням. Це окреме дослідження від nadir-map-
matching, не той самий алгоритм, застосований до іншого кадру.

**Дослідження (2026-09-24) підтвердило: forward/oblique-камера проти
супутникового знімка — НЕ готова технологія для основного джерела
абсолютних фіксів.** Це геометрична проблема ("co-visibility gap" —
навскісний вид бачить фасади/вертикальні структури, яких просто немає на
2D ортофото), не лише питання даних/тренування моделі — тому не зникне
з більшою моделлю. Навіть спеціалізований oblique-пайплайн (NGPS,
arXiv:2607.18936) дає лише ~87% успішних збігів і побудований саме для
фюжну з іншими джерелами, не як самостійний.

- **University-1652** (Zheng et al., ACM MM 2020, arXiv:2002.12186) —
  найрелевантніший готовий бенчмарк: дрон-вид проти супутник-вид, той
  самий сценарій "передня камера дрона проти орто-знімка".
- **TransGeo** (CVPR 2022, arXiv:2204.00097) — дешевий (11.3 GFLOPs/кадр,
  реально на edge GPU типу Spark), але тренований на панорамах з
  вулиці, НЕ на вузькому FOV однієї передньої камери — вузький FOV
  (не панорама) виявився більшою практичною перешкодою, ніж географія.
- Oblique-специфічні роботи 2023-2025 (IEEE 10356107; ISPRS J.
  Photogramm. Remote Sens. 2024) підтверджують: точність падає зі
  зменшенням кута нахилу (більш "вперед", менш "вниз") саме через
  co-visibility gap.

**Рекомендація дослідження**: прототипувати СПЕРШУ place recognition
(NetVLAD/Patch-NetVLAD-стиль, той самий підхід, що вже застосовується для
loop closure в SLAM) проти НАПЕРЕД ЗІБРАНИХ наземних фото вздовж
конкретного маршруту польоту — той самий домен (без cross-view розриву),
дешевше розгорнути, природно личить вузькому FOV передньої камери.
Супутниково-oblique зіставлення (University-1652-стиль) — лише
другорядний fallback для територій без наперед зібраних фото. 3D-mesh
рендер-і-зіставлення — сильніший довгостроковий варіант, якщо є
текстурована 3D-модель місцевості, але дорожчий у підготовці. Жодне з
цього — не заміна GPS без фюжну з іншими джерелами й порогом довіри.

Контекст: нижня (CSI) камера вже дає horizontal-velocity корекцію в EKF
(optical_flow/, `update_ekf_with_flow`) — миттєвий frame-to-frame потік,
без карти/persistent-фіч. Передні камери існують на борту й уже стрімлять
на Spark (GPU, CUDA, там же крутиться YOLO), але навігаційно не
використовуються — лише FPV/детекція об'єктів. `yaw` з MAVLink ATTITUDE —
вже фюжн-вихід FC (враховує компас), тому дрейф курсу НЕ пріоритетна
проблема (перевір калібрування магнетометра/завади від ESC, якщо є
підозра — це апаратне питання, не софтверне).

Три варіанти (від дешевого до дорогого), ранжовано за співвідношенням
зусилля/користь для поточної EKF-архітектури (velocity-domain корекції,
без переходу на factor-graph):

1. **Передня камера як другий вимір швидкості в тому ж EKF** (найдешевше,
   перше, з чого варто починати) — той самий LK/ORB-трекінг, що вже є для
   нижньої камери, просто другий потік кадрів → ще одна корекція
   швидкості. Нижній потік сліпий саме до руху вперед над одноманітною
   поверхнею — передня камера бачить структуру на всіх дистанціях і
   закриває цю сліпу зону. Жодної зміни архітектури фільтра.
2. **Монокулярна depth-модель замість barometer для AGL** (теж дешево,
   лікує вже знайдену слабкість: сирий `baro_alt` — не справжня висота-
   над-землею, зсувається/дрейфує з погодою). FastDepth (Wofk et al.,
   219K параметрів, 178fps на Jetson TX2 GPU) чи MiDaS-Small/
   DepthAnythingV2-Small — реальний час на Spark тривіально. Нюанс:
   більшість таких моделей — relative depth, не метрична; все одно
   потрібен метричний якір (baro чи відома висота калібрування).
3. **Multi-camera MSCKF** (OpenVINS-стиль) — формалізує варіант 1 у
   принципову схему для камер БЕЗ спільного поля зору (нижня+передня
   якраз такі). Джерела: Eckenhoff et al., "Multi-Camera Visual-Inertial
   Navigation with Online Intrinsic and Extrinsic Calibration" (ICRA
   2019); OpenVINS (Geneva/Eckenhoff/Huang, IROS 2019) — референсна
   відкрита реалізація, найдешевша серед VIO за CPU/latency (Delmerico &
   Scaramuzza, Jetson VIO benchmark, arXiv:2103.01655). Потребує
   extrinsic/temporal калібрування камера-камера-IMU (нетривіально для
   рознесених полів зору — саме це вирішує стаття Eckenhoff online).
   Наступний крок ПІСЛЯ варіанту 1, не паралельно.

Розглянуто й відкладено: **VSLAM** (ORB-SLAM3-класу, з loop closure) —
технічно Spark (GPU) потягнув би, але головна цінність VSLAM (розпізнати
вже відвідане місце й виправити накопичений дрейф) не окупається для
одноразового/одностороннього польоту без повернення в ту саму точку. Якщо
в місії з'явиться **автономне RTL без GPS** — це і є "розпізнати вже
бачене місце", тоді VSLAM виправданий; інакше MSCKF (варіант 3) дає майже
весь виграш у точності за набагато менші інженерні витрати (ORB-SLAM3 —
C++ стек, карта, keyframe-менеджмент, окремий інтеграційний проект, не
пара файлів у поточний Python-пайплайн).

Уникати (принаймні зараз): повноцінний оптимізаційний VIO (VINS-Mono,
Qin et al., arXiv:1708.03852, sliding-window bundle adjustment) —
точніший за filter-based підходи, але суттєво дорожчий по CPU/latency й
вимагає заміни EKF на factor-graph estimator — це вже архітектурна
переробка, не розширення поточного фільтра.

Спільні застереження для всіх трьох варіантів: одноманітні сцени
(вода/небо/рівна земля) вб'ють обидва потоки одночасно — лишається просте
IMU-рахування в такі моменти, це не панацея; зараз усе офлайн-replay, для
реального часу знадобиться синхронізація IMU/баро/обох камер по часу,
якої зараз немає (MSCKF чутливіший до похибок таймінгу, ніж поточна
"вільна" frame-to-frame корекція).
