# Sirena Mesh — резервування Starlink через сусідній борт

**Задум:** борти летять групою, у кожного свій Starlink, а між ними — Wi-Fi
mesh (802.11s) на окремому USB-адаптері. Mesh між бортами працює постійно;
на сервер кожен борт іде через свій Starlink. Якщо Starlink борту падає, його
WireGuard (а з ним MAVLink-керування з адмінки, телеметрія і SRT-відео) за ~1с
переходить на Starlink сусіда через mesh. Коли свій Starlink оживає — назад.

Усе, що борт шле на землю, йде всередині WG, тож перемикається ОДИН маршрут —
до WG endpoint. WG-IP борту (10.0.0.x) не міняється, адмінка бачить борт за
тією ж адресою; сервер WG підхоплює нову зовнішню адресу сам (roaming).

## Файли

```
mesh_module/
  mesh-up.sh / mesh-down.sh          802.11s на окремому USB Wi-Fi (oneshot), SAE через wpa_supplicant
  uplink_watchdog.py                 пробник Starlink, маячки, failover, NAT, діагностика :9076
  services/sirena-mesh.service       enabled, стартує при завантаженні
  services/sirena-uplink.service     сторож, BindsTo=sirena-mesh, WantedBy=sirena-mesh
  install.sh / uninstall.sh          /opt/sirena-mesh (ставить install_rpi.sh)
  .env.example                       змінні для /opt/sirena/.env
admin_module/routes/mesh_ui.py       /mesh + /api/devices/<id>/mesh/{status,diag,up,down}
admin_module/services/mesh_control_service.py
admin_module/templates/mesh.html     дашборд кількох бортів
sirena_manager/config.py             сервіс "mesh" (кнопки), не в BOOT_SEQUENCE
```

## Як піднімається mesh (`mesh-up.sh`)

- Чекає до 10с на USB-адаптер з підтримкою **mesh point** і **ніколи не чіпає
  інтерфейс з default у таблиці main** (аплінк). Вбудований `wlan0` (brcmfmac)
  mesh не вміє — відсіюється сам.
- Знімає rfkill лише з phy адаптера, відключає NetworkManager, вимикає power save.
- Перевіряє, що `SIRENA_MESH_FREQ` дозволена регіоном (не disabled / no IR / radar).
- Одна мережа для всіх бортів: однаковий конфіг, IP із MAC адаптера —
  `10.66.<MAC[4]>.<MAC[5]>/16` (`SIRENA_MESH_IP` перевизначає).
  `10.0.0.0/24` зайнята WireGuard, тому `10.66/16`.
- Маршрутизація між бортами — HWMP самого 802.11s, без статичних mpath/arp.
- Вкладається в 18с (`sirena_manager` чекає на `systemctl start` 20с).

## Шифрування (SAE)

- Ключ — `/etc/sirena-mesh/mesh.key` (0600, root), **однаковий на всіх бортах
  групи**. Ставиться інсталятором: `sudo SIRENA_MESH_KEY='<ключ>' bash install_rpi.sh …`
  (або `mesh_module/install.sh`); повторна інсталяція без змінної ключ не чіпає.
- Є ключ — mesh піднімає `wpa_supplicant` (mode=5): SAE (група 19), CCMP,
  обов'язковий PMF (`ieee80211w=2`) — без ключа до mesh не приєднатись, кадри
  не прочитати й не підробити (deauth тощо). Скан лише на частоті mesh
  (`scan_freq`), інакше скан усіх каналів на mt76 — 6с+.
- Нема ключа — `iw mesh join`, відкритий, з попередженням у журналі. Відкритий і
  SAE-борт один одного не бачать: ключ ставити на всі борти разом.
- Сторож перезапускає mesh, якщо `wpa_supplicant` помер. У діагностиці —
  `security: sae|open` (на `/mesh` — рядок «Шифрування»).
- Перевірено: `authorized: yes`, `MFP: yes`; UDP 40 Мбіт/с — 0.1% втрат (як
  без шифрування); failover 1.0с; борт з іншим ключем — plink LISTEN, 0 пакетів.

Кнопка: адмінка → `sirena_manager :9070 /api/v1/services/mesh/{start,stop}` →
`systemctl start|stop sirena-mesh sirena-uplink`. Повторний start — не помилка.

## Failover (`uplink_watchdog.py`)

- **Пробник Starlink:** ICMP echo через Starlink-інтерфейс (SO_BINDTODEVICE,
  обходить і policy routing wg-quick, і наш маршрут через mesh) на WG endpoint +
  1.1.1.1 + 8.8.8.8 паралельно кожні 0.2с. Мертвий — 1с без жодної відповіді;
  ожив — 3с відповідей без розривів. (Послідовний `ping -W1` давав до ~9с на
  виявлення.)
- **Starlink-інтерфейс** — default у таблиці main (`SIRENA_UPLINK_IFACE`
  перевизначає). Не `ip route get <endpoint>`: з повним тунелем той віддає wg0.
  Може з'явитися пізніше за mesh (старт борту) — підхоплюється на ходу.
- **Маячки:** UDP broadcast `10.66.255.255:5077` кожні 0.25с —
  `{host, ip, mac, uplink, via, uc_seen}`; сусід зникає через 1с без маячків.
  Ті самі маячки йдуть ще й unicast кожному сусіду; `uc_seen` — від кого
  unicast доходить.
- **Зависші шляхи HWMP:** після leave/join mesh на одному борті mac80211
  інколи лишає шлях до сусіда зламаним — peer link ESTAB, broadcast ходить,
  а unicast ні ~40с (на стенді — кожен другий рестарт `sirena-mesh`; прапорці
  mpath цього не показують). Якщо сусід 2с не чує нашого unicast —
  `iw mpath del` і ядро знаходить шлях заново (<1с). Шлюзом обирається
  сусід, з яким unicast ходить в обидва боки.
- **Вибір шлюзу:** сусід з `uplink=true` і `via=null` (без ланцюжків), з
  робочим unicast, найсильніший сигнал; поточний не міняється, поки живий.
- **Маршрут:** `ip route replace <endpoint>/32 via <сусід> dev <mesh> proto 99`
  + `conntrack -D` (скинути стару NAT-прив'язку UDP-потоку WG) — в обидва боки.
- **NAT (nft `inet sirena_mesh`):** шлюз — masquerade mesh → Starlink для
  10.66/16; клієнт — власний трафік у mesh під mesh-IP (ядро WG кешує src).
  `forward` — policy drop, дозволено лише mesh → Starlink і відповіді.
- **Повний тунель WG** (`AllowedIPs=0.0.0.0/0`, як на бортах): транзит від
  сусіда на шлюзі отримує fwmark самого wg-quick (`wg show wg0 fwmark`), інакше
  правило `not fwmark → table 51820` загнало б його в НАШ wg0. Не `ip rule`:
  wg-quick додає свої правила без пріоритету — перед першим наявним — і після
  рестарту wg0 наше правило опинялось нижче (перевірено на стенді).
- **Самовідновлення:** якщо USB-адаптер скинувся і mesh point не повернувся
  за 2с — `systemctl restart sirena-mesh` (сторож перезапускається разом з ним).
- **Діагностика:** `GET :9076/api/v1/mesh/diag` — режим (`starlink` / `relay` /
  `none`), шлюз, сусіди з сигналом, час останньої відповіді Starlink.
  На `/mesh` — бейдж на кожному борті і кнопка «Діагн.».

## Результати на стенді (2026-10-07, sirena-P-4 + sirena-P-5, відео увімкнене)

Відмова Starlink імітувалась nft-блоком усього трафіку `eth0` поза LAN
(transient-юніт, знімається сам). Пауза — за безперервним ping 10.0.0.x
через WG з машини оператора (крок 0.2с).

| Тест | Результат |
|---|---|
| Starlink P-4 падає → через P-5 (60с) | одна пауза **1.0с**, повернення без втрат |
| те саме після рестарту wg0 на шлюзі (fwmark) | пауза **1.0с**, повернення без втрат |
| Starlink P-5 падає → через P-4 | перемикання 1.0с, але **скидання USB-адаптера P-5** під відео → провали 6–12с |
| Starlink падає на обох | `none` на обох, без зациклень; відновлення одразу |
| Ребут борту | mesh за ~6с після старту, сусід знайдено, правила в правильному порядку |
| Кнопка через API менеджера | stop прибирає все (адаптер → managed, nft-таблиця), start/повторний start — ок |
| Mesh між бортами | ping ~0.65мс; UDP 40 Мбіт/с, 0.1% втрат |

**Після перенесення адаптерів у USB2-порти** (обидва 480 Мбіт/с, той самий день):

| Тест | Результат |
|---|---|
| Starlink P-5 падає → через P-4 | пауза **0.8с**, повернення без втрат |
| Starlink P-4 падає → через P-5 | пауза **1.0с**, повернення без втрат |
| те саме + UDP 40 Мбіт/с через mesh від борту, що падає (95с) | 0.8с / 1.0с; 0–0.07% втрат iperf; **жодного скидання USB** |
| 8 рестартів `sirena-mesh` на P-5 підряд | unicast до сусіда відновлюється за ≤0.4с після старту (зависання в кожному другому — лікується автоматично); WG без жодної втрати |

## Відомі обмеження / наступні кроки

- **MT7612U ставити лише в USB2-порт (чорний).** На USB3-порту Pi 5
  (mt76x2u) нестабільний під навантаженням:
  `tx urb failed: -71` / `timed out waiting for pending tx` → `reset SuperSpeed`.
  LPM (U1) вимкнено квірком — це прибрало скидання від енергозбереження, але
  не від -71. `mt76_usb disable_usb_sg=1` не допоміг. На ядрі 6.12 (P-4)
  адаптер після reset лишається в mesh point, на 6.18 (P-5) — ні (тому
  самовідновлення). У USB2-порту скидань не було взагалі, у тому числі під
  40 Мбіт/с (див. таблицю вище); USB2 (480 Мбіт/с) з запасом покриває
  реальну пропускну здатність mesh.
- **Потужність передачі:** на стенді борти поруч, сигнал ~-18 dBm (перевантаження
  приймача); `iw set txpower` mt76x2u ігнорує.
- **Failsafe під час перемикання (~1с):** оверрайд стіків з адмінки скидається
  через 0.5с без пакетів — літати в режимі з утриманням позиції
  (Loiter/PosHold), `FS_GCS_TIMEOUT` більший за перемикання.
- `SIRENA_ADMIN_SERVER_URL` / `SIRENA_SRT_HOST` мають бути **WG-адресами**
  (так і є з 1.0.3) — інакше трафік іде повз тунель і через сусіда не пройде.
- Канал сусіда тягне два відеопотоки — покладаємось на adaptive bitrate.
- Повного дублювання пакетів по двох шляхах (без паузи взагалі) нема — можливий
  наступний етап (WG-дублікатор на борту і сервері), якщо 1с паузи замало.
